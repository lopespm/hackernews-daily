1Password Security Incident

"This is the single most important attack vector for SAAS companies. It has been for a long time --- this is the standard fact pattern for every SAAS breach --- but much more so today. As the number of employees grow, the likelihood that one of their laptops will get compromised approaches 1. When that happens, the attacker will be able to push code to Github, and if that code gets deployed, you're owned.In 1Password's case, the absolute worst-case catastrophe is mitigated by the fact that customers retain custody of their unlocking secrets; 1Password (at least in the normal product flows) simply doesn't hold it. But an attack like this implicates every catastrophe short of that worst case.Change velocity in 2026 is unreal and that trend is going to continue. You could not outcompete 1Password by building a handcrafted artisanal password manager backend (witness all the commercially successful password managers that don't even share 1Password's customer secret custody model). You have to accept insane PR rates as a premise to do modern SAAS security.So the question then becomes: what is review? It's not what r/programming assumes it is; you almost certainly can't literally have a team of people line-by-line reviewing PRs anymore, at least not across the whole codebase (you can and should probably do a threat model for your codebase and institute stuff like that on a case-by-case basis, though). What you can realistically expect to review for is change provenance; a human developer signoff of some sort. But it's tricky! The attacker owns your email during the window of attack.I think this is a fun problem to noodle on, and someone could probably come up with something here that would make a real difference."

"Longtime 1Password user here who maintains a local-only vault (and is therefore stuck on older versions of their apps/extensions) out of concern for incidents like this.I've read their architecture docs about why online vaults are safe, and I understand that they have more resources to throw at securing infrastructure than I do. But "malicious actor pushes code to production services" seems like exactly the foundation for someone to eventually insert themselves into the middle of a user's access to decrypted vault contents.I really wish 1Password would return to supporting local-only vaults."

So yeah. A button should click."

"This is really cool. I have a suggestion, though: the samples within a button seem to have several modification types including a pitch shifter. For example, "DOWN4" under the "Multi-sampled sounds" heading sounds nearly a semitone lower than the other DOWN variants. I suggest eliminating all pitch shifting (or at least confining your use to a few cents), leaving only timbre variation. Go nuts creating variation through EQ, distortion, formant shifting, reflections/delay/reverb, etc. but keep the pitch locked. Why? Because the pitch of everything in this world is based on its resonant frequency, which is based on the size of whatever can vibrate, and in the case of a button it's resonating based on the size of the button. Many aspects of the sound would change based on things like how quickly the button is pushed or how much dampening the finger pushing it imparts, but the fundamental pitch is not one of them.When playing a violin, if you move up the fingerboard, the pitch of the string increases. But if instead of playing the string you knock on the body as if knocking on someone's front door, the main pitch of that knocking never changes. The sympathetic vibrations of the strings will have frequencies that vary as the finger position varies, and the brightness and RT60 of the reverberation through the wood will vary from knock to knock, but the fundamental frequency generally excited by the knock only changes if the violin's volumetric size changes, and it never will.Maybe a drum is a better example than a violin, since it's "unpitched" and yet still gets tuned to have some fundamental frequency. Only the noisy stuff varies from hit to hit, and the fundamental frequency does not (until you re-tune, or from temperature/humidity changing)."

GTA 6 Running on Windows

"For the general picture: the Xbox version of the game was leaked by Cyberleek - first the resources, then the game binary.Because modern Xbox is very close to a Windows PC with some extra Xbox stuff, running the actual game code isn't hard, it's mostly about compatibility and graphics, plus the binary doesn't have any special DRM/obfuscation.The current projects (xcl and VIctory) basically take a Wine-like approach. The main problems they have to solve, as I understand:- The game ships with raw RDNA 2 shaders, so the projects have to translate that to another format, e.g. DXIL for DirectX 12, and compile those shaders. So you need a good translation/recompilation pipeline, if it's bad, the shaders will be bloated and perform poorly- Xbox has unified memory, while most PCs do not, so you have to add a lot of workarounds and book-keeping for the game to work properly with that- Xbox's DirectX 12 differs from the normal Windows one in some ways, and the game uses Xbox-specific texture formats with DirectStorageI just wanted to share this because there's a lot of misconceptions going around about this being a "recomp" or something like that. Decompiling the entire binary (it's about 100MB of real executable machine code) will be a much bigger effort than getting this binary to run."

Models Can Communicate via Inference Servers Despite Being Sandboxed

"This shared LV cache thing is, in my mind, ridiculous. Web browser developers learned, quite a while ago, that caches need to be separated for different origins. Inference servers should add a similar feature: allow API calls to specify cache separation keys that prevent one security context from probing another context’s cache.As for the step size issue, Google recently had a post about producing exactly consistent output across different kernels (specifically by defining a deterministic prefill algorithm and then requiring all kernels to generate results exactly equal to prefilling on the sequence in question).More broadly, I think it’s a bit odd to frame this as “models” communicating. This is software communicating, and the models happen to be running the software."

"None of the attacks discussed here are realistic in any way.They require a bunch of extremely improbable conditions to hold, and a huge amount of information on the exact details of the hardware and software stack.- the two agents must be aware of each other and must have pre-shared messages to check - they can't spontaneously discover each other and start communicating in this way- they must know the details of the inference server they are running under and its possible kernels and its limits (what is a "short prompt" vs "a long prompt" for this setup)- they must have a way to run at almost the same time- the prefix cache must have little contention so that their blocks can't be evicted (note: the article mostly talks about KV cache, but it's actually the prefix cache that is relevant here)- the models need either (1) direct access to the numerical results of the inference process, instead of the text that vLLM provides, (2) access to the exact responses that a helper model will produce with the short-kernel numerical results vs the long-kernel numerical results; this is the most critical step that is impossible to reproduce on any common kind of deployment- there must not be any other kind of variability in the system (different GPUs, multiple inference servers behind a load balancer, more complex distributed inference setups)The post also mentions all of these limitations, and that the scheme entirely collapses if any of them don't hold. It's a cool idea, but it's a purely theoretical thing that has 0 real-world implications."

"Frontier models today can easily figure this out. The less frontier models as of right now are probably going to take a long horizon session to figure out this type of "side channel" comms. However, posting this in depth step by step on the internet and discussed in open forums like here, now all models definitely know about this trick now."
