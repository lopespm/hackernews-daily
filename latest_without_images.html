Ghostty 1.4

"These are Ghostty GUI release notes, but I want to take a moment to highlight the libghostty progress we've made since Ghostty 1.3.As a reminder, libghostty is the highly portable, embeddable library that provides core terminal emulation, render state, and more. I always felt that a free, high qualty, lightweight, reusable terminal emulation core would benefit the developer world more than any single GUI application. And that is playing out!It is and always was my true purpose with the Ghostty project (I said this in my first ever talk about Ghostty!). I've jokingly said many times that Ghostty GUI is just a glorified tech demo for libghostty. That's not fair though, because GUI is great and there are really talented people working on it.Since I started the project, Ghostty has always gotten people saying "I don't understand why you'd start a terminal emulator today." Well, the answer is libghostty. It's truly unique and its enabling something special (imo!).Highlights of libghostty since 6 months ago (none of the below was true 6 months ago):- Libghostty has nearly 100% coverage of all of Ghostty's core (and you can compile with flags to remove any of these features for size/safety): https://libghostty.tip.ghostty.org/- Libghostty now builds and is tested (in CI) for: Apple (macOS, iOS, visionOS), Windows (MSVC and GNU), Linux, FreeBSD, Android, WebAssembly, and freestanding (i.e. direct on hardware with no OS).- Libghostty has bindings in pretty much every popular programming language: C, Zig, Go, Swift, Python, Rust, .NET, etc.- Libghostty's memory requirements have dramatically shrunk to enable the portability above. There's still work to do but a single empty terminal now takes 90% less memory. And at scale I've proven 10,000 active (input/output happening) terminals on a Linux server with 4 cores and 8 GB of RAM.- Libghostty powers all JetBrains IDE terminals, over 12.5 million active users. https://blog.jetbrains.com/platform/2026/10/jetbrains-termin...- Libghostty is the most popular core behind the wave of venture-backed "agentic" terminals and editors, such as Herdr, cmux, and many others.- Libghostty is being discussed and has been verbally accepted to replace the terminal core in Neovim: https://github.com/neovim/neovim/pull/39773 (work still to be done)- Libghostty powers a really popular and powerful terminal emulator for emacs (Ghostel): https://github.com/dakra/ghostel- Libghostty's speed is used by Antithesis to fuzz popular terminal programs and has directly led to hundreds of bug fixes sent upstream to programs such as tmux, btop, shells, and other terminal emulators. :)- And so much more: https://github.com/Uzaaft/awesome-libghosttyLibghostty is really successfully turning into the tide that raises all boats. As it becomes more popular, Ghostty itself gets more performant and stable, and so does everyone else. It is also a vehicle for delivering modern terminal emulation to the widest source possible.I plan on tagging libghostty 1.0 in the next few months and declaring ABI stability at that point!"

Solar power is becoming bigger than nuclear

"Unregistered solar is huge in the developing world. In the Philippines, basically no one tells the utility they installed solar, because the net metering application is so expensive, comes with tons of red tape (read as opportunities for government officials to extract bribes), and only gives you billing credits anyway. So people just install batteries and automatic transfer switches. Some even disconnect from the grid completely, or never connect in the first place because it was too expensive to get the line installed. Automatic transfer to a generator is now very simple, and with LPG generators, extremely clean and low maintenance.As I understand it, this is very common across much of the developing world now. So the tracking of how much solar energy there is in the world is almost certainly a lower bound on the reality."

"It's been cheaper than nuclear for a while now, it was only a matter of time.Personally i'm waiting for the next iterations of Kesterite cells.If we can get single cells to crack ~20% efficiency. With a tandem cell architecture, it's going to become the new standard overnight.Durability of silicon cells or better, but orders of magnitude $ cheaper to produce, and without the need to use toxic agents as in perovskite cells.We're movin' fast.For over a decade we were stuck at ~12% efficiency. And in the last 4 years (probably with AI help) we've cracked 15% efficiencyhttps://interestingengineering.com/energy/chinese-researcher...Few more years, and with a bit of luck, we'll all be around to see solar panels that cost 1/10th of what they do now."

"Clarifying "Balcony Solar"I'm seeing a lot of comments mis-representing "balcony solar". This is a phrase that specifically means "small-scale solar panels that directly feed the grid". It is NOT about solar cells feeding a "cooler sized battery+inverter".This is what makes it so attractive; no battery is required. But this is also why it is waiting in the US on legislation (back-feeding the grid). Germany has already passed this legislation. In particular, the equipment needs to be UL3700 certified.See https://en.wikipedia.org/wiki/Balcony_solar_power"

Python's experimental JIT to be removed

"Unfortunate. I've been following the work on it occasionally.On one hand, it seemed like JIT work was really progressing in high gear until SC requested a new PEP. Also unfortunate, as it seemed like part of the hope for the JIT was that it'd counter the performance penalty from free threading.On the other, it did feel (to me) like with all the fancy (and definitely cool) optimizations it got (automatic refcount operation removal, new type-based specializations, inplace math operations), the macrobenchmark benefits weren't _that_ exciting for a JIT. It definitely has potential for more, maybe with even fancier optimizations like unboxing ints, but the complexity just keeps going up.> It said that the PEP was "overly optimistic" about user-visible differences with the JIT enabled.The JIT is technically generated from the same source as the interpreter loop itself, so originally the differences were extremely unlikely, but I imagine the risk just kept going up as new JIT-only paths and optimizations were introduced.And politically, I feel like SC’s reasoning was just “this side project has landed in main branch almost by accident and has been stewing without oversight ever since, with no stabilization in sight”; and the latest PEP was probably still too vague, with a lot of “here’s more things we can add to the stew” - so I can understand if SC wasn’t satisfied."

"Here’s an idea instead (maybe it already exists). Allow a decorator for writing inline Cython. It solves, I think, 90% of the problem. On first run, or eagerly, compile the decorated functions. Basically, Cython is the JIT, and user enables it explicitly.This way I can easily write inlined functions with proper C speed, in a Python esque language.Reasons why I rarely use Cython without this:- unmodified Python code running in Cython is often faster, but not that much. 50% or so is my rule of thumb.- but the development style is very different for Cython and Python, adding a lot of impedance. Eg reloading doesn’t quite work, profiling is different, you need a build directory and a build step at deployment etc.- Cython proper is different enough and I’d argue unintuitive enough that if I have to have all these things in place, I might as well wrap my function in Rust.Such a decorator would give you a low friction way to make things faster when you need it, with scope for making it much faster via all the funny Cython, while keeping Python-esque semantics, in particular "development semantics".I think it would require some language modification since Cython was definitely a superset of Python; I think some of that syntax has been streamlined, but maybe still a strict superset."

"How many Python JIT experiments have failed? I find it interesting because Ruby is probably harder to optimize than Python but Ruby has had a JIT for a long time. Maybe base python is more optimized than base Ruby so the JIT is incrementally not changing much? Also, I'd expect javascript to be harder to optimize but it has JITs. That could just be a funding issue, though. There's probably much more money and incentive to optimize Javascript."
